# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is an **AI coding interview exercise** (not a production codebase). The candidate has 40 minutes to design and implement a lightweight API Gateway using AI tools. Three mock backend microservices are provided; the candidate's solution must live in `gateway/`.

The interviewer observes the session — the evaluation focuses on **how the candidate collaborates with AI**, not just the final result.

## Critical constraint

- **NEVER modify anything under `services/`** — the three mock backends are the fixed interview scaffold. All candidate code goes in `gateway/` (currently empty).
- Do not create extra files at the repo root; the candidate's code belongs inside `gateway/`.

## Commands

Backend services are Go standard-library-only (no `go.mod` in services — they build with plain `go build`).

```bash
docker compose up --build   # one-click startup of all 3 backend services
curl http://localhost:8081/  # user-service    (:8081) — list of users
curl http://localhost:8082/  # order-service   (:8082) — list of orders
curl http://localhost:8083/  # product-service (:8083) — list of products
```

Each service also exposes `/health` (used by Docker healthchecks via `wget`).

Inside a service directory (e.g. `services/user-service`), build/run standalone:

```bash
go build -o server main.go   # CGO_ENABLED=0, matches the Dockerfile
./server                     # listens on :8080 inside the container
```

There are no tests, linters, or CI configured. `graphify-out/` (generated by the `/graphify` knowledge-graph tool) is tooling output — ignore it.

## Architecture

A single-port API Gateway (recommended port `8080`) must route to the backends:

| Route | Backend |
|-------|---------|
| `/api/users/**` | `http://localhost:8081` |
| `/api/orders/**` | `http://localhost:8082` |
| `/api/products/**` | `http://localhost:8083` |

Routing per these rules is the **minimum requirement**; any production-grade gateway features (timeouts, retries, auth, logging, etc.) are bonus.

The three backends (`services/{user,order,product}-service/main.go`) are byte-for-byte identical in structure — each is a single-file `package main` using only `net/http`, `encoding/json`, `log`, `time`:

- A `Response` struct (`service`, `path`, `method`, `timestamp`, `data`) returned by every request
- A hardcoded in-memory data slice (`users` / `orders` / `products`)
- Two handlers registered via `http.HandleFunc`: `/health` → `healthHandler`, everything else → `handler`
- Listens on `:8080` (mapped to host ports 8081/8082/8083 via `docker-compose.yml`)

`docker-compose.yml` builds each service from its `Dockerfile` (multi-stage: `golang:1.22-alpine` builder → `alpine:3.19` runtime, static binary), maps host 808x → container 8080, and adds a `wget http://localhost:8080/health` healthcheck (5s interval, 3 retries).

## Suggested gateway design points (for discussion)

- Read the routing table from config/env rather than hardcoding
- Decide how to handle paths the gateway forwards unchanged vs. rewrites (`/api/users/...` → upstream root or upstream `/...`)
- Timeouts / retries / circuit breaking; request/response logging; structured error responses
- Whether to reverse-proxy only the three known prefixes or also proxy unmatched paths
